# 被切碎的法律条款

> 工程阅读提示：故事中的金额、吞吐量、延迟与评测成绩是场景示例，不代表可复现的生产基准。代码用于解释设计，落地需结合实际版本、数据与测试。

项目进行到第七天。系统终于能够稳定处理文档。然而，第一轮问答评测惨不忍睹。测试人员输入：

“企业版客户超过 30 天，什么情况下还能退款？”

系统检索出了这样一个 Chunk：

> 特殊情况下，可以向商务部门申请审批。审批结果以书面通知为准。

**模型回答：** “超过 30 天可以向商务部门申请审批。”

听起来没错。但测试人员指出：

“它没有说明这是企业版退款政策，也没有解释什么叫特殊情况，更没有引用具体的合同条款。”

林川打开了原始文档。```
第三章 售后服务

3.2 企业版退款政策

3.2.1 常规退款
合同生效后30天内……

3.2.2 特殊退款
超过30天原则上不支持退款。
如存在重大交付违约……
可向商务部门申请审批。
```问题找到了。分块器将一份结构化文档切成了孤立的文本片段。每个 Chunk 只保留了正文。标题、章节和父级语义全部丢失。

“我们不是缺少知识。”

林川说。

“我们是在分块的时候，把知识之间的关系破坏了。”

他决定引入 Heading Path。每个 Chunk 不再只存储正文，还要记录完整章节路径。```
{
  "documentId": "DOC_10086",
  "chunkId": "CHUNK_0032",
  "headingPath": [
    "第三章 售后服务",
    "3.2 企业版退款政策",
    "3.2.2 特殊退款"
  ],
  "content": "超过30天原则上不支持退款……",
  "page": 12,
  "version": 7
}
```用于 Embedding 的文本也可以构造为：

```
第三章 售后服务
> 3.2 企业版退款政策
> 3.2.2 特殊退款

超过30天原则上不支持退款……
```这样，向量模型看到的就不再是一句缺乏背景的话。而是带着章节语义的完整知识片段。但林川很快发现，Heading Path 也不是万能的。有些表格跨越三页，有些条款必须结合上一节理解，有些 PDF 根本没有正确的标题层级。因此他进一步设计了三种策略：

- 结构化分块：适合 Markdown、规范合同、技术手册。
- 父子分块：使用较小的子块进行检索，再返回较大的父块供模型理解。
- 特殊内容分块：表格、代码块、跨页段落使用专门的解析与切分规则。

**周野问：** “那 Chunk Size 应该设置多少？”

**林川回答：** “没有一个适用于所有业务的固定答案。我们需要用真实问答集测试不同大小和重叠比例，比较召回率、上下文噪声、Token 成本和答案质量。”

“不能只因为 512 Token 看起来常见，就认定它是最优值。”
