      一张决定系统命运的架构图

      工程阅读提示：故事中的金额、吞吐量、延迟与评测成绩是场景示例，不代表可复现的生产基准。代码用于解释设计，落地需结合实际版本、数据与测试。

      第二天上午九点。

      林川在白板上画出了系统的第一版架构。

      星云企业级 RAG 平台 · 总体架构

      层次 组件 / 链路
      用户入口 Vue 3 · API Gateway · Spring Security / JWT
      知识入库 文件上传与校验 → 解析 / OCR / 结构识别 → Heading Path 分块 → Embedding 向量化 → PostgreSQL + pgvector
      在线问答 Query 理解 / 改写 → Hybrid Search 混合检索 → Rerank 重排序 → 上下文构造 / LLM → SSE 流式回答 + 引用
      生产能力 权限隔离 · Redis · 消息队列 · 可观测性 · 评测 · 灰度 · 审计

      陈默盯着架构图。

      “为什么要分成两条链路？”

      林川回答：

      “因为知识入库和在线问答的性能要求完全不同。”

      “用户上传一份 500 页的 PDF，解析、分块、向量化可能需要几十秒甚至几分钟。”

      “但用户提问时，不可能等这么久。”

      他写下两组指标。

      链路 核心目标
      离线知识处理 吞吐量、可靠性、可恢复性
      在线问答 低延迟、高可用、答案准确性

      “所以，上传接口不应该同步执行整个知识处理流程。”

      “我们应该把文件保存到对象存储，把任务持久化，然后通过消息队列交给后台 Worker。”

      陈默问：

      “如果 Worker 处理到一半宕机呢？”

      林川回答：

      “任务状态机、幂等处理、重试机制、死信队列和补偿任务。”

      “如果消息重复投递？”

      “使用稳定的任务 ID、数据库唯一约束和状态检查，避免重复产生有效数据。”

      “如果向量写入一半失败？”

      “使用版本化索引。新版本构建完成并校验后，再切换可检索版本。”

      陈默终于露出了笑容。

      “这才像一个生产系统。”

      但他不知道，真正的麻烦才刚刚开始。
